# 配置迁移逻辑的可失败自检

> 适用范围：任何带迁移、归一化、回退兼容或多格式转换逻辑的插件。
> 核心命题：迁移逻辑是最容易写成「永远绿」的代码——它喂进去什么都能跑，断言什么都能过，因为测试用的样例和实现里的分支是同一份直觉。**迁移逻辑的测试必须以「输入是旧格式的真实产物」为准，且必须有一条例外分支的负向样例。**

---

## 一、为什么迁移容易写成一坨永远绿

### 1.1 样例与分支同源

```text
实现：if (!new) return old          # 分支
测试：喂 old，断言等于 old        # 同一个直觉
```

两边来自同一个人在同一分钟里的同一个念头，于是测试只能证明「代码跑过」，证明不了「读的是对的那张表」。

### 1.2 空值与缺省混为一谈

旧格式的字段缺失、新格式的字段为空字符串、两字段都为空——三种情况在 `??` 与 `||` 下走出不同分支，却常常被同一个样例覆盖。

### 1.3 迁移成功后没人看

迁移通常发生在启动路径上，出错不影响主流程，于是「没生效」这件事永远不会有人报告。

---

## 二、自检的四个必备形状

自检是模块导出的一个纯函数：喂旧格式、返回新格式、加断言。放在模块里随模块被复用，不另建外部脚本。

### 2.1 真实旧格式：至少三种

自检样例必须从「用户真实的旧配置」取，不能从「实现认识的形状」取。最低要求三种：

```js
// a) 完整旧格式：所有旧字段都有值
read({ newField: undefined, legacyA: { x: true }, legacyB: { x: true } })
// b) 部分旧格式：只有一半旧字段有值（用户中途用过）
read({ newField: undefined, legacyA: { x: true }, legacyB: {} })
// c) 新旧并存：新字段已写但旧字段仍有残留（迁移后又被手动改过）
read({ newField: { x: true }, legacyA: { x: false }, legacyB: { x: true } })
```

第三种最容易被漏，也最容易出事：它决定「谁是优先真值」。这个判定必须显式写进代码注释，它不是一个实现细节，是一条产品语义。

### 2.2 新旧优先关系必须成对断言

新旧并存时的优先规则要单独断言，且**正反两个方向都测**：

```text
新字段有值 + 旧字段有值 -> 结果等于新字段   （新优先）
新字段为空 + 旧字段有值 -> 结果等于旧字段   （旧回退）
```

只测前者的话，把实现写成「新字段优先」或「旧字段优先」都能过。

### 2.3 覆盖每一类语义，而不是每一个取值

自检的目标是**语义穷举**而非取值穷举。一张转换表比十行断言更有用：

```text
旧字段 A 存在 B 不存在  -> 新字段 = ?   （并集还是交集）
A 存在 B 存在值冲突     -> 新字段 = ?   （谁赢）
A 不存在 B 存在         -> 新字段 = ?
两者都不存在             -> 新字段 = 默认
```

把这张表先写在文档里，再逐格写断言。反过来做（先写代码再补断言）一定会漏掉「你没想到的组合」。

### 2.4 负向样例：证明它真的会拒绝

至少要有一条「输入非法 → 明确报错」的样例。

```text
输入类型不对（数组当对象用） -> 应抛错，而不是静默返回空
输入含宿主不认识的键         -> 应忽略或报错，二选一并写清
```

没有负向样例的迁移函数，实际上什么都接受，出错时会一路静默滑到默认值。

---

## 三、幂等：迁移必须能跑第二次

迁移可能被重复触发（配置重载、重启、热重载、用户手动重跑）。

```text
读(读(旧格式)) == 读(旧格式)     # 幂等必须显式断言
```

自检里加这一条，成本一行，收益是消除一整类「第二次启动后配置变了」的诡异缺陷。

不幂等的典型来源：

- 转换时做了累加或取模（`count + 1`）；
- 以「存在即需迁移」为判据，但迁移本身不清理来源；
- 时间戳、序号、随机值参与输出。

---

## 四、收敛：迁移 + 写入合成一批

迁移的清理动作与主写入放在同一次写入里，理由见 [config-field-lifecycle.md](./config-field-lifecycle.md) 第三节。

自检要覆盖这个批的**形状**，而不只是读取函数：

```js
// 批次形状自检：主写入 + 每条旧字段各一条 unset，共用一次 revision
const ops = buildOps('newField', next, legacyFields)
assert(ops.filter(op => op.op === 'set').length === 1)
assert(ops.filter(op => op.op === 'unset').length === legacyFields.length)
assert(legacyFields.every(field => ops.some(op => op.path[0] === field)))
```

这三条断言各挡一类事故：主写入漏发、清理漏发、清理指向了错误的字段名。字段名写错这件事静态扫描抓不到——它拼错之后仍然是一条合法路径，只是清的不是那个字段。

再加一条门禁级别更狠的：

```js
// 旧字段名必须与 schema 声明的键逐字相等
legacyFields.forEach(field => assert(field in schemaKeys, `${field} 不在 schema 里`))
```

这条能抓住「代码里拼错字段名」「改名后只改了一半」两类事故。

## 五、破坏实测清单

每条自检写完后，逐条人为破坏确认它会红：

```text
把优先关系反写（新优先 <-> 旧优先）  -> 应 FAIL
删掉一个 unset op                    -> 应 FAIL
让 unset 指向拼错的字段名            -> 应 FAIL（靠字段名与 schema 比对那条）
去掉幂等处理（改成累加）            -> 应 FAIL
让类型不对的输入静默返回默认值      -> 应 FAIL
只留旧格式样例、删掉新旧并存样例     -> 自检仍绿——记住这条不是靠破坏实测发现的，是靠设计文档
```

最后一条值得单独强调：**「漏了一个测试场景」这件事破坏实测抓不到**。抓它只能靠那张先写下来的语义转换表。测试能证明已有断言有效，证明不了断言覆盖完整。

---

## 六、门禁分级

```text
必做：读取函数的语义转换表穷举 + 新旧优先双向断言 + 幂等断言
必做：批次形状自检（一条 set、每条旧字段一条 unset、字段名与 schema 比对）
必做：至少一条负向样例
应该：部分旧格式样例（只填一半旧字段）
可选：多条旧格式叠加、多轮重复迁移
```

自检随模块导出后，任何复用该模块的插件都自动获得这些保护——这是把规范写进接口、而不是写进某个脚本的好处。
