# 跨专题工程治理与维护实践

> 本文只记录可迁移的工程判断，不记录具体插件、仓库、技能名称、固定数量、版本号或提交历史。它不替代 DSH API 参考、静默失效指南或具体重构方案。

## 1. 先确定证据等级

### 触发条件

当任务涉及跨模块变更、能力删除、兼容迁移或契约影响面时，先建立影响图，再进入具体 API 专题。

当服务属性、事件顺序、插槽落点、配置语义、构建产物或发布包行为不确定时使用。

### 错误模式

- 把文档意图当成运行时契约。
- 依据方法名或类型名猜调用顺序。
- 启动成功、请求成功或无报错被误认为功能生效。
- 用旧版本经验覆盖当前发布物。

### 验证动作

按证据强度推进：

1. 真实运行时、注册表、浏览器、磁盘或发布包结果。
2. 本地实际加载的实现代码和包元数据。
3. 类型声明和导出面。
4. 官方源码与文档。
5. 记忆和推测只能作为待验证假设。

结论中标明证据属于运行时事实、源码事实、文档说明还是未证实推断。文档与运行时冲突时，先复现差异，再更新说明。

## 2. 用删除测试判断模块深度

### 触发条件

考虑拆分、合并、删除模块或增加一层 adapter 时使用。

### 错误模式

- 只因文件很长就拆分。
- 只因实现很短就删除真实的运行时 adapter seam。
- 把复杂度从一个文件搬到多个浅 module。
- 为了“可测试”复制一套只在测试中使用的生产接线。

### 验证动作

先问：删除这个 module 后，复杂度是消失，还是扩散到调用方？再检查：

- interface 是否小而稳定；
- 调用方是否无需了解缓存、解析、生命周期和兼容细节；
- 是否存在第二个真实消费方；
- 现有集成测试是否已经覆盖该行为面；
- 新 seam 是否减少调用方必须掌握的概念。

只有“第二消费方、共享状态协调、或独立兼容回归”成立时，文件级拆分才有足够依据。

## 3. 保持运行时 adapter 薄，领域 module 纯

### 触发条件

插件同时处理 Host 生命周期、领域判定、Browser 渲染和 CLI 输出时使用。

领域 module -> 运行时 adapter -> Host / Browser / CLI

领域 module 接收普通数据、最小能力接口或显式回调；运行时 adapter 负责注入、事件、权限、资源注册和清理。

### 错误模式

- 领域算法直接拿 Context、浏览器全局对象或进程退出权。
- 事件监听器里混入目录扫描、解析和业务判定。
- CLI 文本格式成为领域 module 的唯一 interface。
- 为测试专门手写一条与生产不同的接线。

### 验证动作

分别测试纯判定、module 组合和真实宿主接线。Provider、Service、Slot 注册等 DSH adapter 应保留真实生命周期测试，不能只测内部 helper。

## 4. 让算法返回结果，让 CLI 负责报告

### 触发条件

同一检查可能被 CLI、CI、测试、编辑器或其他插件复用时使用。

### 推荐结果

结构化结果至少包含 `ok` 和可定位的 `diagnostics`；诊断可继续包含 code、severity、subject、expected、actual 等字段。

### 错误模式

- 算法直接 `console.log` 或决定退出码。
- 测试只能捕获 stdout，无法断言结果。
- 多个调用方重新解析日志文本。
- 用全局开关控制输出，导致并发调用互相影响。

### 验证动作

同一输入应产生同一结果，且不依赖终端。CLI 将结果渲染为文本并决定退出码；CI 可以消费结构化结果；输出格式变化不应改变算法测试。

## 5. 双面插件保持 Host / Browser 物理隔离

### 触发条件

插件同时有宿主入口和浏览器入口时使用。

Host 承担生命周期、服务、权限、文件和持久化；Browser 承担渲染、交互和插槽注册；跨端只通过明确的 RPC、配置表单或事件协议通信。React 组件只接收明确 props，不接收完整 Context。

### 验证动作

检查 Browser 产物不含 Host 依赖；用真实页面确认 slot 确实出现；卸载和 HMR 后没有重复监听或样式；写操作从接口、磁盘或注册表回读，而不是只看组件状态。

## 6. 为每个产物维护 provenance

### 触发条件

源码、编译结果、复制产物或发布包同时存在时使用。

### 错误模式

- 一个产物有多个生成器。
- 测试读源码而发布读旧产物。
- 构建成功但产物来自旧输入。
- 发布清单漏掉运行时真正需要的文件。

### 验证动作

为每个产物记录“输入 -> 生成方式 -> 输出 -> 消费者”。门禁检查来源唯一、内容一致、产物语法和发布清单；必要时做字节比较，不能字节比较时做解析后的结构比较。人为修改产物后，门禁必须失败。

## 7. 缓存失效使用聚合指纹

### 触发条件

缓存目录扫描、解析结果、注册清单或规范快照时使用。

### 错误模式

单看目录 mtime 会漏掉子文件编辑、先建目录后写文件、增删条目和重命名。

### 验证动作

指纹至少组合根目录状态、根级名称集合和关键文件 mtime 或内容摘要。必须覆盖编辑、增加、删除、重命名四类变化，并同时验证上层注册表与本地快照都失效。

性能优化前先测冷读、热读、解析和一致性成本；缓存收益不足以抵偿 stale 数据风险时保持简单实现。

## 8. 集合比较先确认顺序语义

### 触发条件

比较清单、注册项、依赖项、资源集合或配置键集合时使用。

### 错误模式

按数组索引比较导致顺序变化误报，或两侧顺序一致但实体全错时漏报；只比较长度也无法发现属性漂移。

### 验证动作

无序集合按稳定唯一键建 Map；重复数量有意义时使用计数表；顺序有意义时单独断言顺序。测试至少覆盖换序、缺项、多项、重复项和同名属性差异。

## 9. 正则必须服从真实数据域

### 触发条件

用正则识别命令、资源、文件名、标识符或 token 时使用。

### 错误模式

字符类过窄导致规则完全不命中，字符类过宽导致误报，只测正向样例导致门禁恒绿。

### 验证动作

先写清起始字符、后续字符、数字、连字符、命名空间和边界，再测试最短合法值、常见组合、非法字符、相邻标点和近似文本。每条规则至少有一个必须命中和一个必须拒绝的样例。复杂语法应升级为词法扫描或 AST。

## 10. 门禁和 TDD 都要证明失败能力

### 触发条件

新增校验、修复静默失败、改变缓存、产物、权限或错误报告时使用。

1. 先写能复现错误或缺失行为的测试。
2. 在旧实现上运行并确认按预期失败。
3. 写最小实现使其通过。
4. 故意破坏实现，确认测试或门禁再次失败。
5. 还原并运行完整验证。

门禁应给出对象、期望、实际和退出状态。每条新门禁都要完成一次破坏实测。模块自检可下沉到 module interface，但总门禁只编排，不复制规则。

## 11. 写操作后回读权威真值

### 触发条件

配置、文件、表单、注册表、缓存刷新、远程调用或批量操作改变外部状态时使用。

### 错误模式

把点击、请求返回、日志或乐观 UI 当成成功；遮罩、禁用态、部分字段写入和 stale cache 都可能没有报错。

### 验证动作

等待操作结束，从权威来源回读，逐字段比较，必要时连续读取两次确认收敛。浏览器场景额外确认控件可用、事件未被遮罩吞掉、组件只有一份、控制台无错误。

## 12. 删除能力时检查承诺面

### 触发条件

删除命令、工具、服务、插槽、配置字段或资源时使用。

### 验证动作

按消费者清点：运行时入口、Host/Browser 入口、文档、locale、类型和导出、测试 import、编译产物、构建清单、配置 patch、发布清单和记忆文档。用全仓搜索确认没有残留调用、旧文案或旧路径；再跑真实消费者验证。

## 13. 不适用场景

- DSH 具体 API 名称、参数、服务挂载名和版本兼容性：回到官方源码、类型和运行时参考。
- 纯文案、排版或一次性脚本：不必套用完整治理流程。
- 已由现有专题完整覆盖的静默失效、浏览器验收和发布细节：直接阅读对应专题，不重复复制。

## 快速检查

- 证据是运行时真值还是推断？
- 删除测试后复杂度消失还是扩散？
- adapter、领域 module、CLI 的职责是否清楚？
- 算法是否返回结构化结果而不是打印？
- Browser 是否携带了 Host 能力？
- 每个产物是否有唯一来源并经过一致性检查？
- 缓存、集合比较、正则和门禁是否有反例？
- 写操作是否回读权威状态？
- 删除能力是否清理全部承诺面？
