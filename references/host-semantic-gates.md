# 宿主语义门禁：静态断言测不到的那一段

> 适用范围：任何依赖宿主运行时语义的功能——配置写入、注册表仲裁、缓存失效、生命周期、热重载。
> 核心命题：DSH 插件最贵的缺陷不是崩溃，而是「静态门禁全绿、真机完全失效」。原因不是门禁写得差，而是**有一类门禁在原理上无法用静态断言覆盖**：宿主运行时的语义门禁只在真机触发。

> 这篇给出这份清单。写门禁前先对一遍，能省掉一轮「静态全绿、真机零作用」的返工。

---

## 一、为什么静态门禁测不到

静态断言能证明「产物里有这段代码」，不能证明「这段代码在宿主里会走到哪一步」。宿主在链路中间插了闸门时，产物侧完全无感。

典型形态：你的代码、你的测试、你的门禁三方一致地理解错了宿主的某条规则，于是三方一起绿，运行时一起死。

识别信号：

- 桩测试全绿，真机零作用；
- 界面完全正常（能渲染、能点、有状态），但落盘零变化；
- 宿主日志与浏览器控制台都没有对应错误；
- 换个宿主版本或换个 profile 就复现或消失。

## 二、清单

### 2.1 配置写入闸门（真机唯一）

宿主 Settings 服务对每一条写入路径逐条校验是否落在 volatile 节点下，任一条不合法即整批拒绝。

- 静态可测：schema 里字段的 volatile 标注；
- 静态测不到：闸门是否真的拦、拦的是整批还是单条、`unset` 与 `set` 是否同受检。
- 真机判据：人为让批里一条 op 指向非 volatile 字段，观察到**整批零写入**。

详见 [config-field-lifecycle.md](./config-field-lifecycle.md) 第二节。

### 2.2 客户端表单的处置态（真机唯一）

宿主提供的表单对象在被插件卸载或热替换后会被处置（置为已释放状态并停止响应）。此后调用写入接口不会发请求、不会报错、**直接返回失败**。

典型场景：用户在未刷新页面的旧标签页里操作已被热重载替换的插件。读操作看起来一切正常（快照还在），写操作全部静默失败。

- 静态不可测：宿主对象在什么时机被处置。
- 真机判据：热重载后不刷新页面，直接操作 → 观察写入是否零生效。
- 设计要求：**每次写入都要把失败显式呈现给用户**，不能只信返回值的真假。界面上的失败提示与控制台诊断栈是唯一防线。
- 组件侧另外加代际计数，处置后任何迟到的回执静默丢弃，避免卸载后仍改状态。

### 2.3 注册表仲裁（半真机）

同名候选的裁决由宿主的排序规则决定，rank 数值大小在不同版本、不同组合层之间含义可能变化。

- 静态可测：你自己的 rank 声明；
- 静态测不到：别的 provider 实际报了多大、同层重复注册是抛错还是遮蔽、组合顺序是否影响结果。
- 真机判据：构造同名竞争者，正序与反序各注册一次，断言同一条目仍归你；同时断言未受影响的条目独立可用、条目总数不变。
- 只做正向注册测不出顺序依赖。

### 2.4 缓存失效的实时性（半真机）

宿主侧通常有一层目录缓存，你自己可能还有一层候选快照。**两层都要作废才叫生效。**

- 静态可测：你的失效入口是否被调用；
- 静态测不到：宿主的缓存是否真的在你 invalidate 之后刷新。
- 真机判据：改配置 → 读宿主真实注册表（不是读 UI），断言可见集已变。
- 症状：UI 已更新而宿主目录不变，或反之。只测一侧等于没测。

### 2.5 产物缓存时序（半真机）

客户端产物的响应带长期有效且标记为不可变的缓存头，修订号由文件元数据派生而非内容哈希。

由此得到三条：

1. 刷新页面、重开面板、重开设置窗口都**不够**，必须重启宿主进程；
2. **页面上的版本号与界面可能不同步**：版本号来自宿主清单，界面来自产物，两条更新链路独立；
3. 修订号变了不代表内容变了（重写文件会改元数据）。判定要逐字节比对产物内容。

- 静态可测：产物里没有绝对路径、没有开发期残留；
- 真机判据：读页面上的修订号与磁盘产物元数据推算值，比对是否一致。
- 开发期让界面携带一个可读的构建标识（版本号或构建戳），「装的是哪一版」就不必翻产物。

### 2.6 生命周期与卸载（半真机）

宿主支持热重载，会在同一进程内反复重建插件入口。有状态的东西放在模块顶层就是跨代残留。

- 静态可测：注册是否都包在生命周期托管里；
- 真机判据：热重载三次后断言没有重复监听、重复样式标签、重复注册。
- 卸载判据：界面元素消失、样式标签归零、宿主侧注册表条目清空、配置文件无残留影响下次启动。
- 「界面消失」不等于「资源释放」，「资源释放」也不等于「配置已清」。三者分别取证。

### 2.7 插槽的静默注册（半真机）

动态注册在宿主未声明对应插槽规格时**不执行且零报错**。静态扫描产物里出现注册调用，什么都证明不了。

- 静态可测：产物里只出现允许的插槽名。
- 真机判据：目标面板的 DOM 节点计数**恰好为 1**；一个功能一个入口，多落点即污染。
- 「一个功能一个入口」要在多个目标面板各数一遍，只数一个会漏。

### 2.8 文档只读态（半真机）

配置文档处于只读时，宿主不报错，只是拒绝一切写入。

- 真机判据：只读态下界面显示明确横幅、控件全禁。
- 设计要求：把只读态当成一种正常状态渲染，不要让用户面对可点的死控件。

---

### 2.9 插件包元信息与图标体积硬边界（真机硬拦截）

宿主在引导或扫描插件包时，不仅验证配置 Schema 与代码语法，还会硬性校验 `package.json` 引用的静态资源（尤其是 `"icon"`）。

- **宿主硬闸门**：资源物理体积 **不得超过 256 KiB**。
- **为何静态门禁测不到**：TypeScript 编译（`tsc --noEmit`）和针对源码业务逻辑的单元测试只读取代码与类型声明，根本不触碰外部静态图片文件的二进制字节数；只要语法正确，本地编译测试 100% 绿灯。
- **真机表现**：插件安装到 profile 后，宿主启动或插件管理器加载时直接抛出：
  `Plugin metadata for <package>: Error: <path>/package.json: icon exceeds 256 KiB`，导致插件元数据解析损坏、列表卡片白屏或被静默跳过加载。
- **真机判据与安全防线**：
  1. 静态增加针对 `package.json.icon` 指向文件的物理大小断言（硬限制 ≤ 256 KiB，安全警戒线 ≤ 100 KiB）；
  2. 真实桌面/Web 实例启动后，回读插件管理列表，断言插件元信息成功展示且控制台无 `Plugin metadata` 异常日志。

## 三、怎么组织真机判据

### 3.1 逐条独立，不要打包成一个 happy path

每条判据独立触发、独立取证。打成一个大脚本时，第一条失败后面全不执行，你会误以为后面几条也通过了。

### 3.2 每条判据要有「反向证据」

只断言成功不够——永远绿的断言和没有断言一样糟。每条判据配一条破坏实验：

```text
人为让闸门拒写        -> 应观察到整批零写入
人为去掉 volatile 标注 -> 应观察到写入被拒
人为让注册重复执行     -> 应观察到重复资源
人为改坏产物缓存标识   -> 应观察到界面未更新
```

破坏实验做完必须还原并重跑全绿，否则你不知道是判据有效还是本来就红。

### 3.3 真值必须从界面之外取

界面状态、点击结果、截图、退出码都不能单独证明成功。

| 要证明的事 | 取证位置 |
|---|---|
| 配置真的落盘 | 磁盘上的配置文件 |
| 插件真的生效 | 宿主的真实注册表或服务接口 |
| 产物真的是新的 | 产物的字节内容 |
| 版本真的发布了 | 外部包源的元数据与产物下载 |

理想形态是「两侧用同一份文件当唯一事实源，各自观测」：界面读一遍、宿主读一遍、磁盘读一遍，三处一致才算通过。

### 3.4 判定交互要用浏览器原生点击

写操作的自动化点击优先用 DOM 原生的元素点击，命中元素自身、绕开遮罩层。检查点：

- 点之前轮询禁用属性直到解除，否则点击静默无效；
- 收敛判定要求**连续两帧相同且满足目标谓词**，只等谓词会在初始态已满足时立刻通过；
- 长连接会让「文档就绪」类等待永不触发，改用更弱的等待条件；
- 控制台输出流按 UTF-8 处理，否则中文断言全乱码。

### 3.5 浏览器不可用时的降级

没有浏览器工具时，**明确请用户安装**，不要用读 DOM 源码或跑接口替代真实点击——这两者恰好是漏掉遮罩吞点击、控件禁用、渲染失败的主要来源。

降级路径是分层的：先直接调宿主的纯读取函数问真值（比启服务加浏览器快两个数量级），再退到无浏览器探针，最后才请用户装工具。

## 四、验收矩阵

| 形态 | 判据 | 能否静态测 |
|---|---|---|
| 冷安装 | 安装链解析正确、组合树完整 | 部分 |
| 热安装 | 免重启生效、界面自动刷新 | 否 |
| 热更新 | 版本号与界面同步 | 否 |
| 卸载 | 界面消失、资源释放、配置无残留 | 否 |
| 写入 | 落盘且重启后仍在 | 否 |
| 闸门 | 非法路径整批被拒 | 否 |
| 注册表 | 同名裁决与双向一致 | 否 |
| 产物 | 内容与元数据一致 | 部分 |
| 只读 | 横幅与禁用态 | 否 |

这张表就是「哪些断言写在脚本里、哪些必须留到隔离实例」的分工依据。
