# 复现实验设计：前置条件、对照组与可失败断言

排查「宿主行为不符合预期」这类问题时，最贵的错误不是没查到根因，而是**查到了一个假根因**。
假根因的特征是：症状看起来对上了，修复后症状消失，于是结论被写进记忆库，
下一次换一个项目又被同样的假根因骗一次。

本文只讲实验设计。机制语义查各专题：
补全与守卫档位见 [slash-commands-and-input-triggers.md](./slash-commands-and-input-triggers.md)，
宿主写入闸门等真机项见 [host-semantic-gates.md](./host-semantic-gates.md)，
产物与加载链路见 [client-bundle-loading-and-artifact-trace.md](./client-bundle-loading-and-artifact-trace.md)。

## 一、症状不等于状态：先证明状态真的发生了

「界面上没出现我要的东西」至少有两种完全不同的成因，观测结果一模一样：

| 状态 | 成因 | 观测 |
| --- | --- | --- |
| 目标特性从未进入被测状态 | 输入未被上游解析成预期形态 | 症状：无输出 |
| 目标特性已进入被测状态但被下游丢弃 | 上游工作正常，下游过滤掉了 | 症状：无输出 |

**判定动作**：找一个「状态发生过」的可观察标记，只断言这个标记，不看最终输出。
典型标记按可靠性排序：

1. **样式标记**：宿主给「已进入某状态」的节点加了内联样式或 class（最易取，直接读 DOM 属性）；
2. **持久化标记**：状态机把结果落进可回读的存储（配置、事件日志）；
3. **DOM 结构标记**：元素 id、data 属性、分组标题上的来源标记。

**可失败检验**：故意制造「状态没发生」的条件（同一条路径少一个前置步骤），
确认标记随之消失。两边都能观测到，才算证明了这条链路。

## 二、前置条件不是可选的：冷态与热态行为不同

很多系统的目录、注册表、连接池是**懒加载加一次性 ready** 的：
冷态下查询返回空或 false，ready 之后才返回真值。于是同一个操作序列：

- 冷态执行：上游解析不到目标，返回「无结果」；
- 热态执行：上游解析成功，进入目标状态。

**后果**：冷态下的实验，症状与「功能缺陷」完全一致，但两者根因无关。
据此写下「某功能有缺陷」，修复方向会整体跑偏；更糟的是修复后症状确实消失了
（因为顺手把状态焐热了），结论看起来还被验证过。

**判定动作**：把前置条件显式列出来并主动满足它，而不是碰运气。常见的隐式前置：

- 需要先存在一个真实会话或连接（空会话上多数异步管线不启动）；
- 需要先触发过一次加载，让目录或缓存进入 ready；
- 需要先有一次成功的写入，让后续读取有真值可比；
- 需要先完成一次界面挂载，让注入回调真的跑过。

**记录方式**：写进项目记忆库的验收脚本前置段，而不是留在脑子里。
判据是「新开一个环境照文档做能复现」。

## 三、对照组：修同一处，只变一个变量

排查结论要可信，必须能说出「改了什么导致症状变化」。只有「有补丁 vs 无补丁」两组、
而两组之间还有别的差异（构建时间、缓存、配置、启动顺序）时，结论并不成立。

**正确做法**：用同一份源码做两次实验，只切换被怀疑的那一个变量：

1. 取修复前的提交（或临时把补丁摘掉），构建，验证症状在；
2. 恢复补丁，构建，验证症状消失；
3. 中间其他条件（实例、配置、脚本）完全一致。

**收益不止是结论**：这一步会顺带暴露「我的补丁是否引入新问题」。
实践中，正是在对照组里发现原本判为失败的断言其实是脚本断言写错，而不是产品回归——
这类混淆只有对照组能拆开。

**分组纪律**：一次只改一个变量。需要同时改两处才能修好时，
先分别单独改，确认各自贡献，再合并提交。

## 四、断言纪律：断言它自己，不要断言「第一个匹配」

写验收脚本时最常见的自欺是**锚点选错却一直绿**：

- 用「按类型取第一个匹配」当锚点——页面上同类元素多于一种时，
  断言稳定测的是另一个对象，而且每次都通过；
- 用文本内容当锚点——界面语言随环境变，非 ASCII 内容在某些编码链路下变成乱码，
  断言会因为与实现无关的原因失败或永远匹配不上；
- 用「恰好找到一个」当断言——元素数量变化（分组、折叠、懒加载）会让它间歇失败，
  于是被人加个 sleep 掩盖，掩盖掉的是真问题。

**替代锚点，按可靠性排序**：

| 想证明的事 | 可靠锚点 |
| --- | --- |
| 某个功能注册成功 | 该功能注册时写入的标记（属性、id 前缀、分组来源名） |
| 某个列表里有目标项 | 目标项的结构化 id（含来源名与序号），不是文本 |
| 某个状态已生效 | 宿主写进 DOM 或存储的状态标记 |
| 配置真的落盘 | 回读配置文件本身，不看界面 |

**分组标题这一层容易漏**：候选菜单通常按来源分组，条目文本不在第一列。
断言「列表里有某项」若取首列文本，取到的是分组标题而不是条目。
判定时先 dump 一次结构（各层的 role、id、data 属性），按真实结构写断言，不要猜。

**断言必须可失败**：每写一条，用一次人为破坏证明它真的会红。
破坏完必须还原并重跑全绿，否则你不知道是断言有效还是本来就红。

## 五、被测环境自身的不稳定，会伪装成产品缺陷

自动化环境有三个独立于产品的不稳定源，任何一个都会污染结论：

| 源 | 症状 | 处置 |
| --- | --- | --- |
| 凭据或令牌一次性 | 重启实例后旧脚本全失败 | 令牌不写进脚本，从本次启动输出里取；启动后重新读取，不复用上一次的 |
| 网络间歇性 | 同一命令连续失败又连续成功 | 带退避重试；把「可重试」与「确定性失败」分开计数 |
| 输出流被构建日志污染 | 解析结构化输出失败，看起来像工具坏了 | 结构化输出与日志混在同一流时，从特征位置切分后再解析 |

**识别信号**：同一段脚本重跑结果不一致，且失败点在「连不上 / 认证 / 解析」而非「断言不符」。
**处置纪律**：先排除环境，再看产品。把环境问题写进产品缺陷记录，是最难清理的一类污染。

## 六、被测代码的遗留物：声明产物不会自动清理

构建产物里由生成器写出的文件，在源文件被删除后**不会**被自动移除——
生成器只负责覆盖与新增，不负责回收。这类遗留物会：

- 继续出现在打包清单里，成为发出去的一部分；
- 让「产物目录里有哪些文件」与「源码树里有哪些文件」长期不一致；
- 在做清单核对时被人当成正常内容放过。

**判定动作**：打包前把产物目录的文件名集合与源文件集合做一次差集，出现差集即阻断。
**处置**：删除源文件时同步删除对应产物；把这条写进删除流程，否则它会在下一次重构里回来。

**通用形态**：任何「生成物目录加不清理」的组合都有这个问题——类型声明、
代码映射、编译缓存、路由表、旧版本残留，判据与处置完全一样。

## 七、口径漂移：文档里的数字与常量必须跟着产物走

文档里出现的「体积约多少」「上限多少条」「默认多少项」这类数字，
只要是从某次实测抄下来的，就会在下一次改动后变成错的。错的数字比没有数字更有害——
它会被当作规格来验收。

**处置**：每次改动产物或默认值的提交同步更新这些数字；或改成不写具体数值
（「受上限设置约束」），让读者以设置为真源。
**可失败检验**：文档里的数字断言跟随真实产物动态计算，而不是写死期望字符串——
后者会随每次变更一起过期。

## 八、把单次事故沉淀成可迁移规则

事故记录最容易退化成两种形态：流水账（只有时间线和现象），或结论（只有一句断言）。
前者无法复用，后者无法复核。可迁移的中间形态是四段式：

```text
症状：用户在什么操作下看到什么（不含包名与版本）
根因类别：属于哪一类机制问题（状态门禁 / 前置条件 / 断言锚点 / 产物遗留 / 口径漂移）
判定动作：下一次遇到同类症状，第一步该做什么来确认或排除
可失败实验：怎么造出一个必然失败的样例，证明这条规则有效
```

**通用化处理**：把包名、版本号、仓库名、机器路径、固定数量全部换成占位符；
把「这次是这样」改写成「满足这些条件时就会这样」。
一条规则如果只能用具体仓库的例子讲清楚，说明它还没提炼完。
