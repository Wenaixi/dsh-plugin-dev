# 运行时真值与外部契约：构建期常量、跨端挂载、受控控件与文档漂移

> 适用范围：双面 UI 插件里「值明明对，界面却说不对」「宿主日志完全正常但功能是死的」「文档写的和代码做的不是一件事」这一类缺陷。
> 核心命题：**构建期常量、编译期写死的清单、文档里的历史结论，都是会过期的假来源。** 真值在运行时、在请求响应里、在磁盘上。三者对不上时，先问「我引的是哪一层」。

---

## 零、七类假来源速查

| 假来源 | 典型症状 | 真值取证位置 |
| --- | --- | --- |
| 构建期内嵌的常量 | 改了配置项，界面/模型目录停在旧值 | 运行时快照接口的返回体 |
| 编译期写死的贡献清单 | 命名空间永不出现，宿主零报错 | 网关客户端里那份硬编码清单 |
| schema 默认值 | 「配过」与「没配过」不可区分，诊断面板失去判别力 | 磁盘上的配置文件原文 |
| 受控控件的隐式下标 | 控件可点但键盘不可达、指示器滑出轨道 | 控件实现里取值的那一行 |
| 文档里的历史结论 | 教用户去改一个已退役的路径 | 源码与磁盘落点 |
| 形状错误的 schema 门禁 | 断言写着、永远为假，从不红 | 破坏实测（人为打断一次证明它会红） |
| 未解包的远程返回值 | 接口通、宿主无报错、界面永久「不可用」 | 传输层实现里 `return` 的实际形状 |
| 跨端 Schema 里的 transform 闭包 | 配置面板永久显示「通道不可用」、状态卡在 unavailable | 宿主 describe 序列化产物与客户端 validate 报错 |

## 一、跨端 RPC 的命名空间不会自动开通

宿主侧只负责**暴露端点**。端点方法被扫描到，不等于浏览器侧就有了那个命名空间的调用通道——中间还差一步显式挂载。

**症状**：浏览器侧读取某个命名空间永远得到 undefined，界面永久显示「数据不可用 / 请确认宿主版本」之类的提示；宿主日志完全干净，没有任何异常；改名、加字段、换通道类型都修不好它。

**根因形态**：网关客户端侧维护着一份**编译期写死的官方贡献清单**，只遍历这一份。第三方命名空间不在清单里，于是永远不会被创建。

**修法**：第三方必须在客户端侧显式挂载自己的贡献声明。挂载是**异步**的，正确的顺序是先挂载、再建立 store、最后渲染——挂载返回值即就绪信号，**不要写轮询**：

```js
async function apply(ctx) {
  var mounted = null;
  try {
    mounted = await ctx.remote.$mount(CONTRIBUTION);   // 声明式贡献：package / descriptors
  } catch (error) {
    // 部署里没有 remote 服务时降级：卡片照常出现，只读推导段不显示
    if (ctx.logger) ctx.logger.warn('remote 贡献挂载失败：' + String(error));
  }
  ctx.effect(function () {
    return function () { if (mounted) void mounted(); };   // disposer 交给 effect 清理
  }, '插件名: remote contribution');
  var store = mounted === null ? unavailableStore() : createStore(ctx, '命名空间');
}
```

**关键设计**：挂载失败要**降级而不是抛错**。缺少可选能力时，插件的其余部分（卡片渲染、配置读写）必须照常工作。

**自查**：把命名空间字符串在网关客户端源码里搜一遍。若它出现在某份硬编码清单里，你就是清单外的第三方，必须自己挂载。

## 二、贡献描述符与调用契约：codec 与返回信封

贡献声明里的结果描述符带一个模式字段。读源码时会看到「strict」字样，容易误以为必须传某个 schema 库构造的校验函数。**实际契约窄得多**：

- strict 校验只检查**模式字段本身**是否等于 strict，不校验内容形状；
- 解码走描述符上的解码函数，**缺省时原样透传**；
- 因此恒等函数就是合法且充分的实现。

**意义**：不要为了「看起来严谨」引入一个 schema 依赖并把返回体裹一层。返回体只要是 lossless JSON（能被 JSON 往返无损表达）就能直接传。

**自查**：在网关实现里定位「强制 codec」的函数，看它到底断言了哪几个字段。断言之外的自由度就是你的实现空间。

### 2.1 远程调用的返回值是信封，不是裸值

远程方法的返回值带一层成败信封：**成功是 `{ ok: true, value }`，失败是 `{ ok: false, error }`**。把它当裸值用，后果分两种：

- 成功时你读到 `undefined`（因为 `value` 被包在里面），界面显示「数据不可用」；
- 失败时你读到 `{ ok: false, error }` 本身，然后 `undefined` 继续往下传。

**症状**：接口明明通、宿主零报错、界面永久显示「不可用 / 请确认版本」，而且**没有任何异常**——因为没人在解包。

```javascript
// 错
const data = await ctx.remote.myNamespace.snapshot();
render(data.priority);          // data.priority 恒为 undefined

// 对
const response = await ctx.remote.myNamespace.snapshot();
render(response.ok ? response.value : unavailableView());
```

**判据自查**：去目标版本的网关实现里定位「调用远程方法」的那段，看它 `return` 的是不是带 `ok` 的对象。不同的传输层形态不同（有的裸值、有的信封、有的直接抛），**别把一个传输层的解包方式套到另一个上**——同一个项目里 Host↔Client 与 HTTP 直调可能是两套。

**注意失败也有两种形态**：参数形状错、命名空间已卸载这类**准备阶段**的失败会**抛异常**；传输失败、超时、断连这类**传输阶段**的失败则**返回 `ok: false` 信封**。只写 `try/catch` 会漏掉后者，只判 `response.ok` 会漏掉前者——两条都得写。

## 三、运行时推导值：不进 schema、不落盘、不构建期内嵌

「当前生效档位」「诊断链」「由多层来源合并得出的结果」这类值是**推导值**，不是配置。三条独立约束：

### 3.1 不进 schema，也不给 Schema 默认值

给可持久化字段加 Schema 默认值，会让「用户显式写了 X」与「用户什么都没写」在读取端变得**不可区分**——因为校验层会把缺省填成显式值。任何需要表达三态（显式 A / 显式 B / 从未配置）的场景都不能加默认值。

诊断类面板尤其致命：它靠「这一级到底配没配」来解释「我改了为什么没反应」，默认值让判别力归零，界面开始说谎。

### 3.2 不落盘

运行时推导值落盘等于让**过期值遮蔽新值**。典型：只有进程重启才变化的环境变量，落盘后每次会话都被上一次的快照盖住。

### 3.3 必须走运行时下发，不能构建期内嵌

推导值常由**配置项**参与计算（语言、模式、级别）。把结果在构建期算好内嵌进客户端产物，会让**切换配置后仍显示旧值**——因为产物是冻结的常量。

**判据**：一个值如果会随任何用户可改的配置变化，它就必须走运行时通道；构建期内嵌只适用于「所有用户在所有部署里都看到同一个值」的东西。

## 四、描述类文本的长度上限来自宿主配置，不是你的常量

模型目录会按一个上限截断技能/插件描述。**上限值由宿主的配置项决定**，不是某个包里写死的数字；把它当成常量抄进自己的代码，宿主改配置后你的静态断言就会与运行时行为分叉。

**正确做法**：

1. 断言写成「长度不超过当前上限」，上限从宿主源码读出来并标注来源；
2. 超长不是拒绝，是**被截断成省略号**——后果是触发词匹配不到，属于静默失效，必须在发布前拦死；
3. 长度语义按「真实解析后的字符串」算。多行折叠标量（`>`）需要按折叠语义归一后再数，直接数原文行会算错。

## 五、受控控件：值不在选项里，后果不是「不选中」

分段选择器这类受控控件通常用 `options.findIndex(o => o.value === value)` 求下标，据此设置选中态与焦点。**值不在选项里时下标为 -1**，后果是：

- 全部段 `tabIndex = -1`——键盘用户完全不可达；
- 指示器按 -1 定位，整颗滑出轨道。

这是无障碍缺陷，不是视觉瑕疵。

**正确做法**：把「未配置」表达成**末尾追加的一个真实选项**，让 `value` 永远落在选项集合内。

### 5.1 选项集合跨配置状态必须恒定

上面那条只挡住「值不在选项里」一个方向。**另一个方向同样致命：选项按状态条件追加，用户选过一次之后消失。**

**症状**：控件在某状态下是三段；用户选中其中一段后，下次打开只剩两段——那个原本可以自由选回的状态**变成不可达**，配置被单向锁死。用户能离开这个状态，却回不来。

```javascript
// 错：第三段只在「未配置」时存在，用户选过一次就再也回不去
var options = [A, B];
if (!configured) options.push(C);

// 对：选项集合与「当前处于哪一态」无关
var options = [A, B, C];
var value = configured ? A : C;   // 选中态仍然只反映配置值
```

**分类判据（决定条件追加是否合法）**：问「用户配过其中一个值之后，还会不会想选 C？」

- 会 —— C 是**合法配置态**，必须常驻；
- 不会，C 只是「我没配过」的**状态标记** —— 条件追加合理，但此时 C 的语义是「取消配置」而非第四个取值。

这两类段外观完全相同、语义相反。**照抄相邻控件的写法而不问语义，是这类缺陷的主要来源**——同一面板里一个控件该条件追加、另一个该常驻，是完全正常的组合，不能因为「长得像」就统一处理。

常驻方案要同时守住两条不变式：

1. **选中值只反映配置值**，绝不回退到运行时推导值（否则刚安装的用户会看到「像亲手选过一样」的档位）；
2. **常驻段位置固定**（惯例排末尾），让用户已形成的肌肉记忆在配置前后不被打断。

**通用铁律**：第三方受控组件的隐式契约（求值方式、下标越界处理、缺失键行为）必须读源码确认。想表达「派生值」时，另找位置呈现，不要把它塞进受控控件的 `value`。

## 六、宿主配置变更的收敛点

某些服务的值变化**不在你自己的 fiber 上广播**。你在插件里监听配置更新事件，会永远收不到。

**症状**：用户改了配置项，界面不变；重启后正常——但重启前你反复重启浏览器都没用。

**根因形态**：宿主有自己的配置重载通道，服务条目的更新事件只在那个通道上派发，不在插件订阅的事件总线上。

**修法**：不要试图订阅不存在的事件。运行时快照按需重读即可——既然值是通过请求响应拿的，每次读都取最新的，不需要订阅。

## 七、配置与运行态数据的归属维度

宿主的数据根解析函数（环境变量 > 默认目录）**结构上通常不含「实例/配置档」维度**。任何写在它下面的文件，都被同机所有实例共享。

多实例并存时这是真实串扰源：一个实例写，另一个实例读到并当成自己的生效值（读取方往往还有「文件优先于内存」的纠偏逻辑，于是错的更彻底）。

**正确做法**：

1. 实例归属目录由宿主在启动早期提供的上下文服务给出，在整棵插件树挂载前就绪；
2. 宿主真实的多条启动路径（命令行、桌面宿主、网页）都经同一个启动流程，因此运行时必然能拿到；
3. 拿不到时（测试替身、裁剪宿主）退回全局路径，行为与旧版一致——这是降级路径，不是主路径；
4. 迁移旧全局文件时按「有内容 且 本实例侧尚未设过」双条件导入，导入后改名旧文件使幂等；**导入失败只告警，绝不阻断启动**。

## 八、卸载/更新的真实覆盖面：别把「三处清干净」当成全部

卸载与更新各有独立的判定，逐项取证，不要合并：

| 维度 | 判定方式 |
| --- | --- |
| 依赖清单 | 读配置文件里的依赖键 |
| 组合清单 | 读同一文件里的条目数组 |
| 物理包目录 | 查目录是否存在 |
| **补丁条目** | 读补丁文件，看条目是否还在 |
| 自建数据目录 | 查插件自己建的目录 |
| 界面元素 | 页面上目标文案出现次数归零 |

**补丁条目是高频漏项**：包管理器通常只清前三项，插件条目留在用户补丁里。宿主解析时对未知条目 id 的处理往往是**告警并跳过**（非致命），所以表现是「一切正常，只是启动日志里多了一行看不懂的告警」。

**自查**：在包管理器源码里搜补丁文件的写操作。若唯一的写操作是「切换条目的启用/禁用」，那么它**没有删除条目的能力**——这是宿主能力缺口，插件侧修不了，只能如实告知用户手工清理。

## 九、跨端 volatile Schema 必须是无闭包纯数据结构（Schema.transform 传输丢失陷阱）

宿主侧声明的插件 `Config` 会通过 `ctx.settings.describe()` 收集，经 `schema.toJSON()` 序列化后通过跨端 JSON-RPC 传输给浏览器。

### 9.1 致命假象：以为 Schema.transform 可以跨端透传

开发者常误以为在 Host 侧使用 `Schema.transform(Schema.any(), (val) => clean(val)).volatile()` 是完美的容灾清洗手段，既防 Loader 崩溃又完成数据归一化。
**真实契约**：
- `Schema.transform` 内部的 `callback` 是运行在 Node 进程里的 JavaScript 函数；
- `toJSON()` 进行 JSON 序列化时，函数闭包被静默丢弃；
- 浏览器客户端收到后执行 `new Schema(serialized)` 反序列化，得到一个 `callback === undefined` 的 transform 节点；
- 客户端在校验配置草稿时执行 `rehydratedSchema(draft)`，递归到该节点直接抛出 `TypeError: callback is not a function`！
- 宿主底层的 `ConfigFormController.prototype.decode(view)` 捕获该异常，判定校验不通过直接返回 `undefined`；
- 最终导致 `draft.status = 'ready'` 被跳过，状态永远卡死在 `'unavailable'` 或 `'loading'`，界面显示“当前宿主未提供本插件的配置通道，开关暂不可用”。

### 9.2 跨端 Schema 纯数据声明铁律

1. **volatile 节点严禁绑定 transform**：凡是暴露给前端表单的易变字段，Schema 必须保持为纯类型（`Schema.any().default(...).volatile()` 或联合字面量）；
2. **清洗下沉为双端独立纯函数**：数据清洗与容灾提取逻辑坚决不写进 Schema 回调，下沉为 Host 读配置与 Client 读快照两端各自独立的纯函数，实现跨端与容灾的双赢。


**产物指纹的冻结语义**也要一并核清：条目指纹常在进程启动时算好并冻结。**新增条目**会让宿主投递新指纹（刷新即生效），但**替换已有条目的内容不会**触发重算。原地升级要么重启宿主，要么先移除再添加（让条目数量变化触发完整重挂载）。

## 九、文档漂移：退役事实留在文档里会主动误导

插件自带的提示词、技能卡正文是**模型会真的读到的内容**。里面写着一个已退役的配置路径，等于主动教模型去改一个不生效的文件。

**识别方法**：拿文档里的每个路径、每个优先级层数，回源码核对落点。分层数尤其易错——降层后旧文档里的「四级」会让读者按错误的模型推理。

**防漂移的最小门禁**（两条都便宜）：

```js
// 1. 退役表述不得留在模型可读正文里
const retired = body.match(/<退役路径>|<退役链路措辞>/);
if (retired) { console.error('正文含已退役表述：' + retired[0]); ok = false; }

// 2. 文档版本一致性断言跟随真源，不写死
if (!changelog.includes('## [' + pkg.version + ']')) ok = false;
```

第 2 条的写法是重点：**把具体版本号写进门禁，每次发版都要改门禁本身**——改版本时顺手注释掉或干脆漏改，这道门禁就形同虚设。门禁应校验「几处一致」，不是「某处等于某个字符串」。

**门禁必须可失败**：每加一条断言，用人为破坏证明它真会失败。不做破坏实验的门禁，没人知道它是绿着还是根本没跑。
