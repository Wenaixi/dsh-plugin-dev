# 共享字段的能力边界判定与覆写手段

> 适用范围：产品需求是「同一个数据，对模型/机器一侧与对人类一侧要给出不同表现」（本地化、精度档、脱敏、摘要粒度都属此类），而该数据来自一个自己无法改动的上游服务。
> 核心命题：**差异化需求能否实现，取决于上游那份数据在到达消费方之前经过了几道投影、缓存键里有没有对应维度。** 在动代码之前先把这条链路读通，能省掉一轮「方案写完才发现物理上不可能」的返工。

---

## 一、判定程序：沿链路向上游收敛

从「想要的效果」倒着问四个问题，每个答案都必须落到具体文件。

### 1. 找出全部消费方，各自的取值行

同一个数据通常不止一个消费方（本技能库的场景里，模型目录与人类菜单各一处）。把每一处的取值位置记下来：文件、行、读的字段名。

### 2. 向上追到「投影函数」

消费方通常不读原始对象，而读某个**摘要 / 投影**结果。找到它，逐字段列出它到底拷贝了哪些字段。

**这一步是第一个硬门槛**：投影函数没有列出的字段，即使原始对象上带着，也已经在这一层丢失。后面所有「我把数据挂在 metadata / 自定义字段上」的方案都会死在这里。

### 3. 读缓存键的维度

如果两个消费方读的是同一个带缓存的服务，把缓存键的构成维度抄下来（常见维度：工作目录、作用域链、修订号）。

**这一步是第二个硬门槛，也是最容易漏的一步**：缓存键里没有的维度，在这个缓存的生命周期内就是物理上不存在的。此时无论你怎么写「按调用方返回不同值」的 getter，值都在**摘要生成那一步**被拷成了普通字符串，getter 之后根本不会被读。

### 4. 判定作用域参数能否区分调用方

很多服务接受一个「作用域」参数，看起来像是可以为不同调用方返回不同视图。必须核对两个消费方实际传进去的是不是**同一个对象**（例如都来自同一个 agent 会话、同一个工作目录）。若相同，此路不通。

### 5. 收口

四条全过才存在受支持的实现路径。只要有一条不过，需求就是「上游数据模型不支持」，而不是「还没找到写法」。

## 二、字段投影的第二道门：跨端 schema

即使某字段成功通过了服务内的投影层，跨端传输还有一道**独立的**闸门：远程方法的结果 schema。

- 结果 schema 是逐字段声明的白名单；不在其中、也没有放行额外属性的字段，在解码时被丢弃；
- 反向核对：客户端侧的 RPC 贡献声明里写的 result schema，与宿主侧服务的实际返回结构**必须一致**；只改一端会出现「宿主正常、浏览器拿不到字段」；
- 结论要分清：**「没有消费方读」是偏好问题，「过不了 schema」是硬约束**。二者都要在方案里写明，别混为一谈。

## 三、需求不可行时的三条覆写路径

确认上游不支持之后，按下面的顺序评估。三条路各有明确的失效形态，必须逐条对照再决策。

### 路径 A：接受同源（跟随可靠的那一侧）

**做法**：让两个消费方读同一个值，把差异化需求在别处满足（自己提供一块独立界面走自己的通道）。

**代价**：一个消费方失去差异化能力。

**决策判据**：先查这个消费方当前的实现**在宿主里是否本来就不可靠**（缓存到下一会话边界、字段本来就没被消费、控件本来就禁用）。若它本来就是半残的，选 A 反而把「有时对有时不对」变成「恒定正确」——这不是退让，是把不一致消灭掉。

### 路径 B：并列注册（自己再挂一份）

**做法**：向同一个注册表注册自己的一条记录。

**代价，取决于注册表的唯一键设计**：

- 若唯一键是「类型 + 名字」，别人已占用的名字你无法复用，于是只能另起一个名字；
- 注册表**通常只有「新增」没有「移除他人」的操作**；
- 那么「新增」的结果是**共存**而不是**替换**：界面上同一个对象出现两份（一份原样一份本地化），条目总数翻倍。

**这条路的硬判据**：注册前先确认唯一键、以及是否存在按名字移除的 API。两者都不利时，B 制造的是**常态可见的 UI 重复**——比任何静默风险都更容易被用户发现，也更难辩解。

### 路径 C：运行时改写上游对象（monkey patch）

**做法**：上游把远程方法装成服务对象上的一个**属性描述符**（Object.defineProperty 加 getter）时，可以在运行时取出原 getter、替换成包装版、在卸载时还原。包装版只改自己那几条记录，其余原样透传。

**必须逐条核对的失效形态**（三条全是「不报错但没生效」，属于最坏的一类）：

| 失效形态 | 机理 | 门禁怎么写 |
| --- | --- | --- |
| 宿主升级后补丁静默失效 | 可配置标志与 getter 形态都是打包产物的**内部实现**，不是公开契约；改成私有字段或不可配置即失效 | 断言「目标属性当前是可配置描述符」；断言失败时**显式告警而不是静默跳过** |
| 命名空间重建后补丁丢失 | 命名空间卸载时会销毁并**新建**服务对象，补丁挂在旧对象上；重挂载后回到原行为 | 断言「补丁挂载的对象与服务当前持有的对象是同一个」 |
| 上游字段形状变化导致匹配失效 | 包装版按某个字段（常见是 name）匹配自己的记录；上游改了这个字段的命名或筛选逻辑，于是**一条都匹配不上** | 断言「匹配上的条数等于预期条数」，为 0 时告警 |

**决策判据**：把「这条路的失效风险」与「路径 B 的常态可见代价」放在同一张表里比。若前者可以**用门禁变成显式告警**（而不是纯静默），且后者是用户每次都能看见的界面重复，选 C。

**选定 C 之后的强制动作**：把三条失效形态与其核对方法写进项目记忆库，标注「宿主升级时必须重新核对」。否则它会变成「以后再说就是永远不做」的暗债。

### 一条经常被忽略的否决项

为了让上游少显示你的条目而去改**可见性标志**（例如把条目标成「仅程序可见」），要先确认**同一个标志是否被上游的多个功能共用**。若模型侧的路由与人类侧的菜单查的是同一个标志，改它会连带砍掉另一条通路的主功能——为了保住展示文案而砍掉主功能，是净亏损。

## 四、决策记录要求

这类分析的结论必须落成可复核的文字，而不是停留在对话里：

1. **写清链路**：每个消费方的取值行 → 投影函数 → 缓存键构成，逐项带出处；
2. **写清封口**：哪一条把方案堵死的，以及为什么这不是「还没找到写法」；
3. **写清选定路径的代价**：包括已知失效形态与升级时的核对清单；
4. **留下破坏实测**：每条封口结论配一个可执行的验证（临时改一处，证明结论成立），否则无法区分「结论正确」与「根本没验证」。

## 五、通用检查清单

| 检查项 | 判定动作 |
| --- | --- |
| 消费方是否已全部找出 | 全仓检索该字段名的每一处读取点，别只查自己关心的那一侧 |
| 投影函数拷贝了哪些字段 | 抄出它的解构列表，比对需求字段是否在内 |
| 缓存键包含哪些维度 | 把构成维度的构造代码抄下来，逐个问「这一维变化会重算吗」 |
| 作用域参数能否区分调用方 | 对比两个消费方实际传入的对象引用是否同一 |
| 跨端 schema 是否放行该字段 | 查结果 schema 的字段白名单与解码行为 |
| 注册表唯一键与移除能力 | 确认「能否复用别人的名字」与「能否按名字移除」 |
| 上游消费方当前可靠性 | 读它的缓存失效时机，判断现状是否本来就半残 |
| 选定路径的失效形态 | 逐条列机理，并确认每条都能被门禁转成显式告警 |
